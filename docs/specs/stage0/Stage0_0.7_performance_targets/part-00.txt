1. 성능 목표의 기본 철학
────────────────────────────────────────

1.1 정확성 우선

최적화 우선순위는 다음과 같다.

1. 인과적 일관성
2. 상태 보존
3. 결정론과 재현성
4. 저장·복원 가능성
5. 장기 안정성
6. 처리량
7. 렌더링 품질

성능을 이유로 다음을 허용하지 않는다.

- 원인 없는 결과 생성
- 화면 밖 지역 정지
- 카메라 밖 개체 삭제
- 도시·국가·기술 자동 생성
- LOD 전환 시 자원 보정
- 사건 원인 삭제
- 렌더링 상태를 권위 상태로 사용
- 숨은 성공률·사망률 조정

1.2 측정 가능한 목표

모든 성능 목표는 다음을 가져야 한다.

- 기준 하드웨어
- 기준 설정
- 기준 세계 상태
- 시드
- 코드 빌드 ID
- 측정 시간
- 평균
- 중앙값
- p95
- p99
- 최대값
- 메모리 증가율
- 결과 digest

1.3 성능 모드 분리

프로젝트는 세 성능 모드를 구분한다.

A. Interactive Mode
- 사용자가 세계를 3D로 관찰
- 활성 지역을 상세 계산
- 렌더링과 UI 동시 실행
- 부드러운 입력·카메라·선택 필요

B. Accelerated Mode
- 시간 가속
- 활성 상세 범위를 줄이거나 일부 지역을 집계
- 렌더링은 유지할 수 있으나 프레임보다 틱 처리량 우선

C. Headless Research Mode
- 렌더링 없음
- 장기 실험과 반복 실행
- 모든 지역은 필요한 최소 정밀도만 사용
- 세계 연도 처리량과 재현성 우선

각 모드의 성능 수치를 혼합 평가하지 않는다.

3. 기준 시간 모델
────────────────────────────────────────

3.1 논리 틱

초기 기준:

- Interactive authoritative tick: 초당 10틱
- 1 base tick: 100ms의 상세 시뮬레이션 시간
- 렌더링: 별도 프레임
- 물리적으로 필요한 경우 활성 지역 내부에서 micro-step 사용

3.2 Physics Micro-step

초기 상한:
- 최대 20ms 시뮬레이션 시간
- base tick당 최대 5회

규칙:
- 모든 지역에서 항상 5회 수행하지 않음
- 충돌·고속 이동·구조 불안정이 있는 활성 지역에만 적용
- micro-step 결과는 base tick Commit에 통합
- micro-step은 Event를 불필요하게 폭증시키지 않음

3.3 저주파 시스템

예시 초기 주기:

- 대사: 1~10틱
- 체온: 1~10틱
- 식물 성장: 100틱 이상
- 토양 변화: 1,000틱 이상
- 침식: 10,000틱 이상
- 관계 집계: 10~100틱
- 지역 통계: 100틱 이상
- 장기 역사 압축: 10,000틱 이상

정확한 주기는 각 모듈 구현 단계에서 측정 후 확정한다.

3.4 시간 가속

시간 가속은 base tick 의미를 변경하지 않는다.

허용:
- 단위 실제 시간당 더 많은 tick 처리
- 비관찰 지역의 LOD 강등
- 저주파 시스템의 안전한 batch 실행
- 거시 집계 모델 사용

금지:
- 같은 LOD와 같은 조건에서 시간 배속에 따라 다른 규칙 사용
- 빠른 진행을 위해 결과 임의 생성
- 인과관계를 생략하는 비공개 fast-forward

────────────────────────────────────────
11. 메모리 안정성 목표
────────────────────────────────────────

Warm-up:
- 첫 100,000 tick 또는 시나리오별 정의 구간

Warm-up 이후:
- 로그·Snapshot 보존량을 제외한 메모리 증가율
  1,000,000 tick당 1% 이하

24시간 Soak:
- 비의도 메모리 증가 5% 이하
- 참조되지 않는 Entity/Component 잔존 없음
- 파괴된 Entity는 Tombstone 정책에 맞게 축약
- allocator fragmentation 20% 이하

Steady-state allocation:

12. 사건 처리 성능
────────────────────────────────────────

Event 생성:

지속 처리량:
- H1에서 50,000 Event/s 이상

피크:
- 200,000 Event/s를 10초 이상 처리

Event append latency:
- 평균 2ms 이하/batch
- p95 10ms 이하/batch

Event 크기:
- significant event 압축 평균 256B 이하
- historical event 압축 평균 512B 이하

저장 증가:
- 1,000,000 significant Event당 256MB 이하 목표
- 색인 포함 384MB 이하 목표

원장 조회:

- EventId 단일 조회: 5ms 이하
- Entity 최근 1,000 Event: 50ms 이하
- Region·tick 범위 10,000 Event: 100ms 이하
- 인과 그래프 1,000 node: 200ms 이하
- 인과 그래프 10,000 node: 비동기, 2초 이하

규칙:
모든 미세 물리 적분을 장기 Event로 저장하지 않는다.
중요 상태 변화와 원인 링크를 보존하면서 micro-event를 집계한다.
