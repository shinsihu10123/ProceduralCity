Stage 0.4 개발 규칙 명세

문서 버전: 0.4.0
상태: 기준안 확정
적용 범위: 프로젝트 전체 코드, 데이터, 테스트, 도구, 문서
상위 문서:
- Stage 0.1 프로젝트 철학 및 시스템 경계 명세
- Stage 0.2 핵심 원칙 및 강제 규칙 명세
- Stage 0.3 전체 아키텍처 명세

목적:
Stage 0.3 아키텍처를 실제 구현할 때 발생할 수 있는 상태 오염, 비결정성,
모듈 결합, 저장 불일치, 병렬 처리 충돌, 테스트 부재, 성능 회귀를 방지한다.

────────────────────────────────────────
1. 규칙 등급
────────────────────────────────────────

MUST
반드시 준수한다. 위반 코드는 병합하지 않는다.

SHOULD
특별한 사유가 없다면 준수한다. 위반 시 근거와 대안을 기록한다.

MAY
프로젝트 상황에 따라 선택적으로 적용할 수 있다.

MUST NOT
절대 허용하지 않는다. 발견 즉시 수정하거나 제거한다.

────────────────────────────────────────
2. 개발 원칙
────────────────────────────────────────

D-01. 아키텍처 우선
- 기능 구현은 Stage 0.3의 모듈 경계와 상태 소유권을 따라야 한다.
- 편의를 위해 모듈 경계를 우회해서는 안 된다.
- 빠른 임시 구현도 권위 상태의 직접 수정은 허용하지 않는다.

D-02. 상태보다 명령
- 외부 모듈은 상태를 직접 바꾸지 않고 Command 또는 Intent를 제출한다.
- 상태 소유 모듈이 유효성, 비용, 충돌, 실패를 판정한다.

D-03. 결과보다 원인
- “도시 생성”, “기술 해금”, “국가 생성” 같은 결과 명령을 작성하지 않는다.
- 하위 조건과 상호작용을 구현한다.

D-04. 재현 가능성
- 동일한 코드 버전, 초기 상태, 설정, 시드에서는 가능한 한 같은 결과를 내야 한다.
- 재현성에 영향을 주는 요소는 모두 저장하거나 기록한다.

D-05. 관찰 가능성
- 상태 변경, 성능 비용, 실패 원인을 추적할 수 있어야 한다.
- 디버깅 불가능한 비공개 상태를 만들지 않는다.

D-06. 장기 실행 안정성
- 짧은 데모가 아니라 수백만 틱 이상 연속 실행을 기준으로 설계한다.
- 누수, 수치 발산, 이벤트 폭증, 저장 증가율을 상시 검증한다.

────────────────────────────────────────
3. 상태 소유권 규칙
────────────────────────────────────────

D-STATE-01
모든 권위 상태에는 단 하나의 소유 모듈이 있어야 한다.
MUST

D-STATE-02
다른 모듈의 내부 컬렉션, 배열, 객체 참조를 통해 상태를 직접 수정해서는 안 된다.
MUST NOT

D-STATE-03
외부에 노출되는 상태는 불변 읽기 모델, 복사본, 핸들 또는 제한된 뷰여야 한다.
MUST

D-STATE-04
공유 가변 싱글턴을 사용해서는 안 된다.
MUST NOT

D-STATE-05
전역 접근 가능한 서비스는 다음 기반 서비스로 제한한다.
- 시간
- ID
- 관리형 난수
- 로그
- 구성 읽기
- 작업 스케줄러
MUST

D-STATE-06
권위 상태 변경은 틱의 Commit 단계에서만 확정한다.
MUST

D-STATE-07
틱 처리 중 생성된 임시 변경안은 Commit 이전에 취소 가능해야 한다.
SHOULD

D-STATE-08
상태 변경은 변경 전후 검증을 거쳐야 한다.
MUST

검증 예:
- ID 참조 유효성
- 자원 총량
- 에너지 범위
- 생명 상태
- 위치 유효성
- 중복 소유권
- 음수 재고
- 이미 폐기된 개체 참조

────────────────────────────────────────
4. 시간과 틱 규칙
────────────────────────────────────────

D-TIME-01
시뮬레이션은 고정 틱으로 진행한다.
MUST

D-TIME-02
렌더링 프레임 시간(delta frame time)을 시뮬레이션 판정에 사용해서는 안 된다.
MUST NOT

D-TIME-03
모든 지속 시간은 시뮬레이션 시간 단위로 표현한다.
MUST

D-TIME-04
시스템별 업데이트 주기는 명시적으로 등록한다.
MUST

예:
- 충돌: 매 틱
- 대사: 매 틱 또는 짧은 주기
- 식물 성장: 저주파
- 침식: 장주기
- 인구 집계: 저주파

D-TIME-05
느린 시스템을 매 틱 실행하지 않는다.
SHOULD

D-TIME-06
시간 배속은 한 틱의 의미를 변경하지 않고, 단위 실제 시간당 처리 틱 수만 변경한다.
MUST

D-TIME-07
일시정지 상태에서는 권위 상태가 변경되어서는 안 된다.
MUST NOT

예외:
- UI 상태
- 디버그 카메라
- 저장 요청 대기
- 비시뮬레이션 분석 작업

D-TIME-08
틱 오버런이 발생하면 틱을 건너뛰기보다 처리 지연을 기록한다.
MUST

────────────────────────────────────────
5. 명령과 Intent 규칙
────────────────────────────────────────

D-CMD-01
Command는 요청된 행동을 표현하며 성공 결과를 포함하지 않는다.
MUST

좋은 예:
- MoveIntent(destination)
- PickupIntent(target)
- ConsumeIntent(item)
- AttachIntent(part_a, part_b)
- CommunicateIntent(receiver, signal)

나쁜 예:
- TeleportTo(destination)
- InstantlyBuildHouse()
- GiveKnowledge(technology)
- CreateNation()

D-CMD-02
모든 Command는 고유 ID를 가져야 한다.
MUST

D-CMD-03
Command에는 최소한 다음이 포함되어야 한다.
- command_id
- issuer_id
- issued_tick
- command_type
- target 또는 위치
- 사용하려는 자원
- 예상 소요 시간
- 인지 근거 또는 source_observation_ids
MUST

D-CMD-04
Command 검증은 다음 단계로 분리한다.
1. 형식 검증
2. 참조 검증
3. 권한·행동 가능성 검증
4. 자원·에너지 예약
5. 물리·공간 충돌 검증
6. 최종 판정
MUST

D-CMD-05
동일 자원을 여러 Command가 동시에 예약할 경우 명시된 충돌 해결 규칙을 사용한다.
MUST

D-CMD-06
실패 결과는 실패 코드와 원인을 포함해야 한다.
MUST

예:
- OUT_OF_RANGE
- INSUFFICIENT_ENERGY
- TARGET_GONE
- RESOURCE_CONFLICT
- PHYSICALLY_BLOCKED
- UNKNOWN_TO_ACTOR
- INTERRUPTED
- STRUCTURALLY_INVALID

D-CMD-07
실패한 Command도 필요한 경우 사건 또는 학습 입력으로 기록한다.
MUST

────────────────────────────────────────
6. 판정과 커밋 규칙
────────────────────────────────────────

D-RES-01
Resolution은 권위 상태를 직접 수정하지 않고 StateDelta를 생성한다.
MUST

D-RES-02
StateDelta에는 다음이 포함되어야 한다.
- 대상 상태
- 이전 값 요약
- 변경 값
- 원인 Command
- 관련 Event
- 자원 입출력
- 난수 추적
- 검증 결과
MUST

D-RES-03
StateCommitter는 StateDelta를 원자적으로 적용한다.
MUST

D-RES-04
일부 변경만 적용되어 모순 상태가 생기는 것을 금지한다.
MUST NOT

D-RES-05
부분 성공이 가능한 행동은 부분 성공 규칙을 명시한다.
MUST

D-RES-06
Commit 실패 시 해당 변경 묶음을 롤백하거나 적용하지 않는다.
MUST

D-RES-07
Commit 후 불변 조건을 다시 검증한다.
MUST

────────────────────────────────────────
7. 사건과 로그 규칙
────────────────────────────────────────

D-EVENT-01
사건은 상태 변경 후 생성한다.
MUST

D-EVENT-02
상태를 변경하지 않는 관찰·시도도 분석상 중요하면 사건으로 남길 수 있다.
MAY

D-EVENT-03
사건에는 최소 다음이 포함되어야 한다.
- event_id
- event_type
- tick
- location
- actor_ids
- target_ids
- command_id
- cause_event_ids
- outcome
- before_digest
- after_digest
- random_trace
- intervention_flag
MUST

D-EVENT-04
사건 유형은 버전 관리되는 식별자를 사용한다.
MUST

D-EVENT-05
로그 메시지 문자열을 데이터 계약으로 사용해서는 안 된다.
MUST NOT

D-EVENT-06
사건 원장은 불변 추가 방식으로 기록한다.
SHOULD

D-EVENT-07
과거 사건을 수정해야 하는 경우 원본을 덮어쓰기보다 정정 사건을 추가한다.
SHOULD

D-EVENT-08
모든 미세 상태 변경을 영구 사건으로 저장하지 않는다.
MAY

사건 수준:
- Trace: 개발 전용
- Detail: 짧은 기간 보존
- Significant: 장기 보존
- Historical: 영구 또는 장기 압축 보존

D-EVENT-09
역사 압축 시 인과 연결을 보존한다.
MUST

8. 난수와 결정론 규칙
────────────────────────────────────────

D-RNG-01
모든 난수는 RandomService를 통해 생성한다.
MUST

D-RNG-02
언어 또는 엔진의 전역 난수 함수를 직접 사용하지 않는다.
MUST NOT

D-RNG-03
난수 스트림은 시스템·지역·개체 또는 작업 단위로 분리할 수 있어야 한다.
MUST

D-RNG-04
난수 호출 순서가 무관한 시스템에 영향을 주지 않도록 스트림을 분리한다.
SHOULD

D-RNG-05
중요 판정은 난수 입력을 재현할 수 있어야 한다.
MUST

D-RNG-06
다음 값을 저장한다.
- 세계 초기 시드
- 스트림 식별자
- 스트림 상태 또는 결정론적 파생 규칙
- 저장 시점의 난수 상태
MUST

D-RNG-07
확률은 실제 조건 계산 뒤 불확실성 표현에만 사용한다.
MUST

D-RNG-08
원하는 결과를 만들기 위한 재추첨 또는 숨은 난수 조정을 금지한다.
MUST NOT

────────────────────────────────────────
9. 병렬 처리 규칙
────────────────────────────────────────

D-PAR-01
병렬 처리는 독립 작업에만 적용한다.
MUST

D-PAR-02
동일 권위 상태를 여러 작업이 동시에 수정해서는 안 된다.
MUST NOT

D-PAR-03
병렬 작업은 읽기 스냅샷을 기준으로 계산하고 변경안을 별도로 출력한다.
MUST

D-PAR-04
병렬 단계 사이에는 명시적 동기화 장벽을 둔다.
MUST

D-PAR-05
병합 순서가 결과에 영향을 줄 경우 안정적인 정렬 기준을 사용한다.
MUST

정렬 기준 예:
- tick
- region_id
- entity_id
- command_id

D-PAR-06
스레드 실행 순서에 따라 결과가 달라지는 경쟁 상태를 허용하지 않는다.
MUST NOT

D-PAR-07
락을 사용하기 전에 데이터 분할과 단계 분리를 우선 검토한다.
SHOULD

D-PAR-08
병렬화로 결정론이 깨지는 모듈은 문서화하고 재현성 테스트를 별도로 둔다.
MUST

10. LOD와 다중 해상도 규칙
────────────────────────────────────────

D-LOD-01
LOD 변경은 명시된 승격·강등 정책을 통해서만 수행한다.
MUST

D-LOD-02
LOD 변경 전후 보존해야 할 수량을 정의한다.
MUST

필수:
- 인구
- 물질·자원
- 주요 개체
- 관계
- 지식 분포
- 구조물 핵심 상태
- 영토·통제
- 인과 연결

D-LOD-03
LOD 강등은 세부 상태를 AggregateState로 변환한다.
MUST

D-LOD-04
LOD 승격은 AggregateState와 Seed를 사용해 세부 상태를 복원한다.
MUST

D-LOD-05
복원된 상태는 축약 기간 통계와 모순되어서는 안 된다.
MUST NOT

D-LOD-06
카메라 거리만으로 LOD를 결정하지 않는다.
MUST NOT

추가 기준:
- 사건 중요도
- 추적 대상
- 상호작용 밀도
- 불안정 상태
- 정밀 판정 필요성

D-LOD-07
LOD 전환으로 문명에 보너스나 패널티를 주어서는 안 된다.
MUST NOT

D-LOD-08
LOD 모델별 오차 범위를 측정한다.
MUST

11. 저장과 복원 규칙
────────────────────────────────────────

D-SAVE-01
저장은 일관된 틱 경계에서 생성한다.
MUST

D-SAVE-02
저장 중 변경되는 권위 상태를 직접 순회하지 않는다.
MUST NOT

방법:
- 불변 Snapshot
- Copy-on-write
- 일시적 Commit 장벽

D-SAVE-03
저장 데이터에는 다음이 포함되어야 한다.
- world_tick
- world_time
- configuration_version
- schema_version
- code_build_id
- random_state
- entity_registry
- module_states
- event_segment_position
- intervention_history
MUST

D-SAVE-04
각 모듈은 자신의 직렬화 스키마와 버전을 소유한다.
MUST

D-SAVE-05
저장 파일은 체크섬을 포함해야 한다.
MUST

D-SAVE-06
불러오기 후 다음을 검사한다.
- 스키마 호환
- 참조 무결성
- 자원 보존
- 난수 상태
- 사건 위치
- 틱 일관성
MUST

D-SAVE-07
저장 파일 마이그레이션은 원본을 보존한 상태에서 수행한다.
MUST

D-SAVE-08
마이그레이션 실패 시 일부만 변환된 파일을 사용하지 않는다.
MUST NOT

D-SAVE-09
저장→복원→재실행 결과를 자동 비교하는 테스트를 둔다.
MUST

23. Definition of Done
────────────────────────────────────────

기능은 다음 조건을 모두 충족해야 완료로 처리한다.

1. 요구한 현상을 실제로 표현한다.
2. 프로젝트 철학과 핵심 원칙을 위반하지 않는다.
3. 올바른 모듈이 상태를 소유한다.
4. Command → Resolution → Commit 경로를 따른다.
5. 실패와 충돌 처리가 있다.
6. 인과 사건이 기록된다.
7. 난수가 관리된다.
8. 저장·복원이 가능하다.
9. 단위·통합·재현 테스트가 있다.
10. 성능 영향이 측정됐다.
11. 관련 문서와 용어집이 갱신됐다.
12. 디버그 관찰 경로가 있다.
13. 코드 리뷰 조건을 통과했다.

하나라도 충족하지 않으면 완료가 아니다.
