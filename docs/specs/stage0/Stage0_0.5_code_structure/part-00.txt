Stage 0.5 코드 구조 명세

문서 버전: 0.5.0
상태: 기준안 확정
적용 범위: 프로젝트 전체 저장소, 패키지, 모듈, 테스트, 도구, 문서
상위 문서:
- Stage 0.1 프로젝트 철학 및 시스템 경계 명세
- Stage 0.2 핵심 원칙 및 강제 규칙 명세
- Stage 0.3 전체 아키텍처 명세
- Stage 0.4 개발 규칙 명세

목적:
아키텍처와 개발 규칙을 실제 저장소 구조로 변환한다.
기술 스택과 엔진 선택 이전에도 유지되는 논리적 코드 경계를 정의하고,
향후 언어·엔진이 결정되면 이 구조를 해당 빌드 시스템과 패키지 체계에 매핑한다.

────────────────────────────────────────
1. 기본 방침
────────────────────────────────────────

1.1 기술 스택 독립성

본 문서의 디렉터리명과 패키지 경계는 논리적 기준이다.

향후 다음 중 어떤 구현 기술을 선택하더라도 구조 원칙은 유지한다.

- 자체 엔진
- Unity
- Unreal Engine
- Godot
- Rust/C++ 기반 네이티브 엔진
- 서버 시뮬레이션 + 별도 렌더 클라이언트

기술 스택에 따라 실제 확장자, 프로젝트 파일, 빌드 스크립트는 달라질 수 있다.

1.2 모듈 우선 구조

코드는 화면 기능이나 개발 단계보다 책임 모듈을 기준으로 배치한다.

금지:
- “Phase1”, “Phase2” 디렉터리에 기능 코드를 누적
- “Managers” 폴더에 서로 다른 상태 소유자를 혼합
- “Utils” 폴더에 도메인 규칙을 숨김
- 렌더링 코드와 시뮬레이션 코어를 같은 모듈에 배치

1.3 의존 방향

의존 방향은 다음을 기본으로 한다.

Platform
→ Kernel
→ Foundation
→ Domain
→ Observation
→ Presentation

정확히는 상위 표현 계층이 하위 계층의 공개 계약에 의존한다.
하위 계층은 상위 계층 구현을 참조하지 않는다.

1.4 계약 중심 통신

모듈 간 통신은 다음 계약으로 제한한다.

- Query
- Command
- Event
- Snapshot
- Port/Adapter

내부 클래스나 가변 컬렉션을 외부에 노출하지 않는다.

1.5 저장소 형태

초기에는 단일 저장소(monorepo)를 사용한다.

이유:
- 시뮬레이션 코어와 렌더링·도구·테스트의 버전을 함께 관리
- Command/Event/State 계약 변경을 원자적으로 반영
- 저장 스키마와 마이그레이션을 같은 변경에서 검증
- 초기 개발 단계에서 패키지 분산 복잡도 방지

후속 분리 조건:
- 서버·클라이언트가 독립 배포 주기를 가짐
- 외부 SDK 제공 필요
- 빌드 시간과 접근 권한 분리가 필요
- 계약이 충분히 안정됨

3. 루트 파일
────────────────────────────────────────

3.1 README.md

포함:
- 프로젝트 정의
- 현재 Stage
- 빌드·실행 방법
- 헤드리스 실행 방법
- 테스트 실행 방법
- 저장소 구조 요약
- 핵심 금지 원칙
- 문서 링크

포함하지 않음:
- 세부 아키텍처 전체
- 장문의 설계 근거
- 임시 작업 메모

3.2 LICENSE

프로젝트 라이선스.

라이선스는 Stage 0.8에서 실제로 확정한다.

3.3 CHANGELOG.md

사용자·개발자에게 의미 있는 변경을 버전별로 기록한다.

세부 커밋 목록을 복제하지 않는다.

3.4 CODEOWNERS

핵심 경로별 리뷰 책임을 지정한다.

초기 1인 개발이어도 경로별 책임 범위를 명확히 한다.

예:
- /src/kernel/
- /src/world/
- /src/physics/
- /schemas/
- /docs/architecture/
- /tests/determinism/

3.5 .editorconfig

줄바꿈, 들여쓰기, 문자 인코딩, 파일 끝 개행을 통일한다.

기본:
- UTF-8
- LF
- 마지막 줄 개행
- 공백 기반 들여쓰기 또는 언어별 표준
- 후행 공백 제거

3.6 .gitattributes

대용량·바이너리·줄바꿈 정책을 정의한다.

5. config/
────────────────────────────────────────

목적:
실행 시 사용하는 버전 관리 가능한 구성 파일을 저장한다.

구조:

config/
├─ base/
├─ development/
├─ test/
├─ benchmark/
├─ experiments/
└─ examples/

5.1 base/

프로젝트 기본 상수와 기본 실행 설정.

5.2 development/

개발 편의 설정.

예:
- 상세 로그
- 디버그 오버레이
- 낮은 개체 수
- 빠른 저장 주기

5.3 test/

결정론·단위·통합 테스트용 고정 설정.

5.4 benchmark/

성능 비교를 위한 고정된 시나리오 설정.

5.5 experiments/

실험별 설정.

각 실험은 다음 메타데이터를 포함한다.
- experiment_id
- 목적
- 초기 시드
- 변경 변수
- 기준 설정
- 실행 반복 횟수
- 결과 저장 위치

5.6 examples/

사용자와 개발자를 위한 최소 예제 설정.

규칙:
- 구성 키는 schemas/config에서 정의
- 코드에 중복된 기본값을 흩어놓지 않음
- 모든 실행은 실제 사용한 설정 해시를 기록

10. src/kernel/
────────────────────────────────────────

역할:
모든 도메인이 공유하는 시뮬레이션 실행 코어.

구조:

src/kernel/
├─ api/
├─ host/
├─ time/
├─ ids/
├─ random/
├─ scheduling/
├─ commands/
├─ resolution/
├─ commit/
├─ events/
├─ snapshots/
├─ diagnostics/
└─ internal/

10.1 api/

외부 모듈이 사용할 공개 계약.

10.2 host/

SimulationHost와 lifecycle.

10.3 time/

TimeService, Tick, Duration, update frequency.

10.4 ids/

EntityId, CommandId, EventId, RegionId.

10.5 random/

RandomService와 stream derivation.

10.6 scheduling/

Phase, job dependency, deterministic merge order.

10.7 commands/

CommandEnvelope, CommandBus, 공통 Command metadata.

도메인별 payload는 소유 모듈에 둔다.

10.8 resolution/

공통 Resolution pipeline interface와 Result type.

도메인별 판정 로직은 도메인 모듈에 둔다.

10.9 commit/

StateDelta, CommitBatch, StateCommitter.

10.10 events/

EventEnvelope, EventLedger interface, severity.

10.11 snapshots/

Snapshot publication infrastructure.

10.12 diagnostics/

불변 조건, tick trace, deterministic digest.
