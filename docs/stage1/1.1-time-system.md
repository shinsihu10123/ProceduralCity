# Stage 1.1 — Authoritative Time System

Status: **PASS**  
Decision date: 2026-08-04  
Base branch: `stage0-rebuild`  
Implementation branch: `stage1-time-service`

## Context

Stage 0 established a deterministic fixed-tick kernel with checkpoint restoration, but intentionally kept time as a minimal counter. Stage 1.1 formalizes simulation time as an authoritative service without changing the Stage 0 public host lifecycle.

The world must support indefinite deterministic progression, save/load continuity, time-scale-independent outcomes, and future multi-rate systems such as climate, biology, AI, and erosion.

## Decision

### Authoritative clock

- `Tick(u64)` is the only authoritative simulation ordering value.
- The baseline duration is 100,000,000 ns, or 100 ms per tick.
- Tick advancement uses checked integer arithmetic and never wraps.
- Wall-clock time and render-frame time are excluded from authoritative state.

### Transactional advancement

A tick advances through:

1. `begin_tick`
2. domain calculation and state preparation
3. `commit_tick`

`abort_tick` discards an incomplete transaction. The published tick changes only at commit. Saving during an incomplete tick is rejected.

### Time scaling

`TimeScale` controls processing pace only. It does not change tick duration or simulation semantics. Equal tick counts under different multipliers must produce equal world time and deterministic state.

### Periodic systems

`UpdateCadence` provides deterministic interval and phase-offset scheduling. It prevents all low-frequency systems from clustering on the same tick while preserving replay stability.

### Persistence

`TimeSaveStateV1` stores:

- schema version
- current committed tick
- fixed tick duration in nanoseconds

Unknown schemas and zero-duration states are rejected. Runtime pacing state is not persisted as world state.

### Compatibility

`SimulationHost` preserves the Stage 0 API:

- `new`
- `start`
- `pause`
- `step`
- `checkpoint`
- `restore`
- deterministic digest

The host now delegates authoritative time ownership to `TimeService`.

## Rejected alternatives

### Floating-point elapsed seconds

Rejected because accumulated rounding error and platform-sensitive arithmetic would weaken deterministic replay.

### Variable simulation delta per frame

Rejected because rendering performance would alter world outcomes.

### Tick skipping under load

Rejected because skipped causal steps would make outcomes depend on hardware performance.

### Persisting wall-clock and time scale

Rejected because they are execution-environment concerns rather than intrinsic world state.
